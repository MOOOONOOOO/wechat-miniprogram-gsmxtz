# 决战作品之巅：Codex 实施文档

> 文档状态：可直接实施
> 产品名称：`决战作品之巅`
> 模式标识：`songTournament`
> 适用工程：当前微信小程序仓库

## 1. 产品目标

在现有微信小程序中增加一个单人歌曲二选一淘汰赛。

用户选择一位歌手，系统自动从该歌手的歌曲中组成 16 首或 32 首参赛池。用户确认名单后，系统随机生成固定对阵。用户按轮次连续完成二选一，最终决出冠军、亚军和季军，并生成一张可以回顾完整选择过程的决选表。

这个模式的核心体验是：

> 如果这些作品必须一轮轮相遇，最后你会留下哪一首？

## 2. 核心规则

### 2.1 比赛规模

支持两种规模：

- 16 首赛：`16 → 8 → 4 → 2 → 1`
- 32 首赛：`32 → 16 → 8 → 4 → 2 → 1`

主淘汰赛结束后，两位半决赛败者额外进行一场季军赛。

因此：

- 16 首赛共有 4 轮主淘汰赛、1 场季军赛，共 16 次选择。
- 32 首赛共有 5 轮主淘汰赛、1 场季军赛，共 32 次选择。

### 2.2 晋级规则

- 每场比赛只有两首歌。
- 用户必须选择其中一首晋级。
- 不允许平局。
- 每轮全部比赛完成后，才能进入下一轮。
- 决赛胜者为冠军，决赛败者为亚军。
- 两位半决赛败者进入季军赛，季军赛胜者为季军。
- 季军赛败者不再单独排名。

### 2.3 对阵规则

- 用户确认参赛名单后，系统随机生成一次对阵。
- 比赛开始后，参赛名单和对阵关系锁定。
- 退出并重新进入时，对阵关系不能改变。
- 不设置种子歌曲、轮空、败者复活、双败淘汰或积分排名。

## 3. 完整用户流程

```text
首页“决战作品之巅”
  → 选择 1 位歌手
  → 选择 16 首赛或 32 首赛
  → 系统自动组成参赛池
  → 用户查看并替换不合适的歌曲
  → 用户确认参赛名单
  → 系统随机生成并锁定对阵
  → 按轮次逐场二选一
  → 两位半决赛败者进行季军赛
  → 决赛决出冠军和亚军
  → 展示冠军及前三名
  → 查看完整决选表
  → 保存冠军海报或完整决选长图
```

## 4. 首页入口

首页增加一个独立入口：

- 名称：`决战作品之巅`
- 说明：`从一位歌手的 16/32 首作品中，选出你的最终前三名`

点击后进入歌手选择页。

该模式是单人玩法，不要求用户先填写头像和昵称。

## 5. 选择歌手

- 复用当前程序已有的歌手选择能力。
- 用户只能选择一位歌手。
- 选择完成后进入比赛设置。
- 不改变现有歌手默契、同担 Top、歌词分享等模式的选择流程。

页面主要文案：

- 标题：`选择 1 位歌手`
- 按钮：`下一步：设置决选`

## 6. 选择比赛规模

用户选择：

- `16 首 · 16 次选择`
- `32 首 · 32 次选择`

默认选择 16 首。

页面说明：

> 16 首节奏更快，32 首能容纳更多作品。两种比赛都会决出冠军、亚军和季军。

如果当前找到的歌曲不足 32 首，32 首选项不可用，并提示用户可以进行 16 首赛。

如果当前找到的歌曲不足 16 首，不允许开始比赛，提示用户更换歌手。

## 7. 自动组成参赛池

第一版不提供从零开始的手动选歌模式。

系统按照用户选择的规模，自动组成 16 首或 32 首参赛歌曲。

自动组池应尽量避免同一条歌曲数据被重复加入，但不同的现场版、重制版、Remix 或合作版本可以作为不同作品存在。

组成完成后，必须先展示完整参赛名单，不得直接开始比赛。

页面展示：

- 歌手名称。
- 比赛规模。
- 16 首或 32 首参赛歌曲。
- 每首歌曲的封面、歌名和专辑名。
- `换一批`。
- 每首歌曲旁的 `替换`。
- `确认名单并抽签`。

## 8. 赛前替换

赛前替换是对自动参赛池的局部调整，不是手动选歌模式。

用户点击某首歌曲旁的“替换”后，可以从该歌手其他未入选歌曲中选择一首，替换当前歌曲。

适用情况包括：

- 用户不熟悉这首歌。
- 用户不希望某个现场版、Remix 或重制版参加。
- 用户认为某首合作歌曲不适合进入本次决选。
- 用户更希望另一首作品参加。

替换规则：

- 替换后参赛歌曲总数保持不变。
- 已经在参赛池中的歌曲不能被重复选入。
- 用户可以替换任意数量的歌曲。
- 用户也可以点击“换一批”，让系统重新生成整个参赛池。
- 只有用户点击“确认名单并抽签”后，比赛才正式开始。
- 比赛开始后不再允许替换歌曲。

## 9. 二选一比赛页

每次只展示一场对决。

页面必须包含：

- 当前阶段，例如 `32 进 16`、`半决赛`、`季军赛`或`最终决战`。
- 当前阶段进度，例如 `第 3 场 / 共 16 场`。
- 两张同等视觉权重的歌曲卡片。
- 歌曲封面、歌名和专辑名。
- 两张卡片之间的 `VS`。
- `撤销上一场`。
- `查看当前战况`。

用户点击其中一首后：

1. 被选歌曲显示“晋级”。
2. 未被选择的歌曲弱化。
3. 短暂停顿后进入下一场。
4. 选择结果立即保存。

同一场快速连续点击不能产生两次选择。

## 10. 轮次节奏

每轮完成后，展示一次该轮结果，再进入下一轮。

建议文案：

- 32 进 16：`初次交锋`
- 16 进 8：`渐入佳境`
- 8 进 4：`八强决选`
- 半决赛：`本命候选`
- 季军赛：`最后一个席位`
- 决赛：`最终决战`

决赛固定提问：

> 如果只能留下一首，你会选择哪一首？

### 10.1 季军赛与决赛顺序

半决赛完成后，比赛顺序固定为：

1. 先进行季军赛。
2. 再进行决赛。
3. 决赛完成后统一揭晓前三名。

这样可以把冠军对决保留为整场游戏的最后一次选择。

季军赛页面必须明确说明：

> 两首半决赛遗珠，将争夺最后一个前三席位。

## 11. 撤销与退出恢复

### 11.1 撤销

- 用户只能撤销最近一次选择。
- 撤销后回到上一场重新选择。
- 如果撤销会影响后续已经产生的结果，受影响的后续结果应同时失效。
- 正式完成比赛并进入最终结果页后，不再提供撤销。

### 11.2 自动保存

- 每次选择后立即保存当前进度。
- 用户中途退出小程序后，比赛进度不能丢失。
- 用户再次点击“决战作品之巅”时，如果存在未完成比赛，应询问：
  - `继续上次决选`
  - `重新开始`
  - `取消`
- 选择重新开始前必须再次确认，避免误删进度。
- 同一时间只保留一局未完成比赛。

## 12. 结果页

结果页首先展示冠军，然后展示完整前三名。

### 12.1 冠军区

必须展示：

- `你的冠军作品是`
- 冠军歌曲大封面。
- 冠军歌名。
- 歌手名。
- 专辑名。
- `从 16 首作品、16 次选择中胜出`，或 `从 32 首作品、32 次选择中胜出`。

### 12.2 最终三强

必须展示清晰排名：

1. 冠军
2. 亚军
3. 季军

三首歌曲都展示封面、歌名和专辑名。

不得把两位半决赛败者并列展示为第三名。第三名只能由季军赛产生。

### 12.3 冠军晋级路线

展示冠军每轮战胜的对手，例如：

```text
第一轮  战胜《歌曲 A》
第二轮  战胜《歌曲 B》
八强赛  战胜《歌曲 C》
半决赛  战胜《歌曲 D》
决赛    战胜《歌曲 E》
```

季军赛不属于冠军晋级路线。

### 12.4 结果操作

结果页提供：

- `保存冠军海报`
- `保存完整决选表`
- `再玩一次`
- `返回首页`

“再玩一次”保留当前歌手，但重新生成参赛池和对阵，不覆盖已经完成的历史记录。

## 13. 完整决选表

完整决选表参考用户提供的纸面表格：最左侧是全部初始参赛歌曲，向右依次展示每一轮晋级结果，最右侧突出冠军。

32 首赛：

```text
参赛歌曲 → 32进16 → 16进8 → 八强 → 四强 → 决赛 → 冠军
```

16 首赛：

```text
参赛歌曲 → 16进8 → 八强 → 四强 → 决赛 → 冠军
```

表格还需要独立标出季军赛：

```text
半决赛败者 A vs 半决赛败者 B → 季军
```

产品要求：

- 能从表格中追溯每首歌在哪一轮被淘汰。
- 能看出每场比赛的胜者如何进入下一轮。
- 冠军、亚军和季军必须明显标记。
- 小程序内支持横向查看完整表格。
- 长歌名不能遮挡相邻格子。
- 封面缺失时使用统一的文字或色块占位，不显示破图。

具体页面结构、表格渲染方式和滚动方案由 Codex 根据微信小程序能力决定。

## 14. 图片输出

需要生成两种图片。

### 14.1 冠军海报

用于微信聊天或朋友圈传播，重点展示：

- `决战作品之巅`
- 歌手名称。
- 冠军大封面和歌名。
- 亚军、季军的小封面和排名。
- `从 16/32 首作品中脱颖而出`。
- 指向小程序首页的小程序码。

### 14.2 完整决选长图

用于保存完整选择记录，重点展示：

- 全部初始参赛歌曲。
- 每轮晋级结果。
- 季军赛结果。
- 冠军、亚军和季军。
- 歌手名称和完成日期。
- 指向小程序首页的小程序码。

完整长图应优先保证文字可读，不要求把所有歌曲封面都放大展示。

图片保存沿用当前小程序已有的分享图片体验：优先打开系统图片分享菜单，不支持时回退保存到相册。

小程序码生成失败时可以保留空白区域，但不能绘制假二维码。

## 15. 历史记录

增加“我的决选记录”。

每条记录展示：

- 歌手名称。
- 比赛规模。
- 冠军歌曲。
- 亚军歌曲。
- 季军歌曲。
- 完成时间。

支持：

- 重新打开结果。
- 重新保存两种图片。
- 删除记录。

删除前必须确认，删除后不可恢复。

第一版的比赛进度和完成记录保存在当前设备，不要求跨设备同步。

## 16. 分享边界

第一版不提供好友进入同一场比赛或查看本地完整结果的能力。

- 微信分享卡片可以把朋友带到小程序首页。
- 冠军海报和完整决选长图才是本次结果的主要分享方式。
- 分享文案不得让用户误以为朋友点击后能读取这局本地比赛数据。
- 不为本模式新增好友作答、双人默契、多人排行或公开结果链接。

## 17. 异常情况

至少正确处理：

- 歌曲数据加载失败：提供重试和返回。
- 歌曲不足 16 首：不能开始比赛，提示更换歌手。
- 歌曲不足 32 首：只能进行 16 首赛。
- 替换搜索没有结果：保留原歌曲并允许重新搜索。
- 封面加载失败：使用占位图形。
- 中途退出：自动保存，重新进入可继续。
- 本地记录损坏：不能白屏或卡死，应提示记录无法恢复。
- 图片生成失败：提示重试，不能保存空白图片。
- 小程序码生成失败：海报其他内容仍然可以生成。

## 18. 第一版不包含

- 手动从零选择 16/32 首歌曲。
- 好友作答或猜测用户的选择。
- 双人默契和多人排名。
- 音乐播放和试听。
- 8 首、64 首或自定义规模。
- 败者复活、双败淘汰和积分赛。
- 种子歌曲或人为安排对阵。
- 跨设备进度同步。
- 修改已有玩法的产品逻辑。
- 为该模式新增云函数或云数据库集合。

## 19. Codex 实施要求

工程拆分、页面数量、数据结构、状态管理、测试组织和 Canvas 实现方式由执行 Codex 根据当前项目代码决定。

实施时必须遵守：

1. 先阅读当前项目结构和未提交改动。
2. 保留其他任务正在进行的代码，不覆盖或回退无关改动。
3. 优先复用现有歌手搜索、歌曲读取、缓存、封面处理、海报保存和小程序码能力。
4. 不改变现有模式的操作和数据结果。
5. 比赛对阵、撤销、保存恢复和前三名计算必须具备可验证的独立逻辑。
6. 16 首和 32 首两种流程都必须验证。
7. 完成后运行相关 JavaScript 语法检查和 `git diff --check`。
8. 最终说明改动范围、验证结果、未验证项目和已知限制。

如果实现过程中出现会改变上述产品规则的问题，Codex 必须先向用户确认；纯工程实现选择由 Codex自行决定。

## 20. 验收标准

只有满足以下条件，才能认为第一版完成：

1. 用户可以选择一位歌手并完成 16 首或 32 首决选。
2. 参赛歌曲由系统自动生成，并能在开赛前逐首替换。
3. 确认名单后，对阵固定且退出重进不会改变。
4. 16 首赛总计完成 16 次选择，32 首赛总计完成 32 次选择。
5. 季军由两位半决赛败者通过额外二选一产生。
6. 季军赛先于决赛进行，决赛是最后一次选择。
7. 最终结果准确展示冠军、亚军和季军。
8. 可以回看完整决选表和冠军晋级路线。
9. 未完成比赛能够继续，完成结果能够从历史记录重新打开。
10. 冠军海报和完整决选长图都能真实生成并保存。
11. 没有新增好友玩法、云端比赛数据或其他超出第一版的功能。
12. 现有模式没有因本功能发生行为变化。
